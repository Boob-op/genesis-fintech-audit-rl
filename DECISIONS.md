# Решения и открытые контракты

Редакция 1. Этот файл фиксирует рабочие решения, а не новые требования организаторов. Обозначения: принято — выбираем как проектную основу; проект — нужно утвердить примерами и проверками в указанном блоке; внешнее — требует сведений организаторов, но независимая работа продолжается.

## Принятые основания

| ID | Решение | Причина |
|---|---|---|
| D01 | Python 3.11, небольшое приложение, без UI/LLM/БД в обязательной части | Приоритет проверяемого ядра |
| D02 | Сначала правильная история, затем мутация | Эталон должен объяснять реальное расхождение |
| D03 | Публичный контракт ошибок общий, независимый расчёт отдельный | Избежать согласованной ошибки генератора и проверяющего |
| D04 | Truth builder, независимая проверка и matcher — разные обязанности | Oracle не является независимым доказательством |
| D05 | Reset с seed вызывается доверенным supervisor | Агент должен видеть задачу, но не seed |
| D06 | Процессное разделение дополняется проверкой файловых/сетевых прав | Отдельный процесс того же пользователя не обеспечивает изоляцию |
| D07 | Деньги: integer minor units; FX: Decimal; policy задаёт округление | Детерминизм и точность |
| D08 | Закрытая диагностика и фактическая награда доступны владельцу запуска, не worker | Корректные отчёты без подсказок агенту |
| D09 | Функции CLI запланированы как `python -m fintech_audit_rl <command>` | Одинаковая точка входа для Windows и контейнера |
| D10 | Пользователь утвердил план редакции 4 до завершения проекта; правила закреплены в AGENTS.md | Продолжать по существующим задачам, обновлять прогресс и синхронизировать полный документ; не перепланировать без основания |
| D11 | По прямому запросу пользователя подготовить GitHub-репозиторий и инфраструктуру Б01 до окончания Б00 | Это независимая подготовка окружения, не утверждение открытых финансовых контрактов. Следующая предметная задача остаётся Б00.2 |

## Проекты контрактов: закрыть в Б00, уточнять перед зависимым модулем

| ID | Вопрос | Рабочее предложение | Условие закрытия |
|---|---|---|---|
| Q01 | Таксономия | `duplicate_invoice`, `partial_allocation`, `fx_date_or_rate`, `period_cutoff`; первый — повторное отражение счёта | Согласовать с внешними адаптерами; закрепить в error_spec |
| Q02 | Сумма/валюта/affected_ids каждого типа | Отдельное правило и ручной пример для каждого; нельзя автоматически считать остаток долга ошибкой | Четыре паспорта ошибок и четыре чистых аналога |
| Q03 | Доказательство отсутствующего распределения | Не требовать несуществующую allocation-row; доказать по платёжному документу, связям и полному относящемуся набору записей | Сценарий полного отсутствия разрешим через инструменты за бюджет |
| Q04 | Формат invoice_refs и распределённых сумм | Зафиксировать документированную структуру без удаления обязательных полей PDF | Пример частичного/разбитого/валютного платежа и схема |
| Q05 | ID для FX и policy | Стабильный публичный ID/ключ, доступный через существующие действия; однозначный namespace row/doc IDs | Evidence resolver находит каждый возможный evidence ID |
| Q06 | Период | Политика явно задаёт границы и локальную зону; proposed interval [start,end), timestamp со смещением | Ручные примеры до/на/после границы; не выдать предложение за правило PDF |
| Q07 | Допуски и округление | После детерминированного округления default tolerance=0; иное только явно в spec | FX-примеры, валюты разной разрядности |
| Q08 | Сотый шаг | При допустимом по времени submit на шаге 100 — terminated; сотое исследование без submit — truncated | Таблица переходов и сверка с опубликованным тестом при наличии |
| Q09 | inspection_steps | Считать все расходующие шаг действия до submit, включая ошибки; submit исключить | Примеры reward и единое правило для логгера/oracle |
| Q10 | Закрытый reward в step | Публичный reward=0 как placeholder, scored reward отдельно у оценщика | Явный режим, совместимость адаптеров, тест отсутствия утечек |
| Q11 | Невалидный submit | -1 на стороне оценщика, terminated, обобщённый публичный статус; подробности только в закрытом журнале | Разделение структурной ошибки и валидного, но неверного finding |
| Q12 | Неизвестный тип, лишние поля и неверный episode_id | Явно определить schema-invalid против valid-but-wrong; не размывать FP структурной валидацией | Таблица негативных входов согласована со схемой |
| Q13 | Нормализация | Порядок ID не влияет, лишние уникальные ID сохраняются; лимиты до нормализации; повтор finding — FP | Тесты повторов внутри списков и между findings |
| Q14 | Дополнительные evidence IDs и просмотр доказательств | Полный допустимый набор обязателен; отдельно решить неизвестные/лишние ID. Не добавлять требование «агент обязан ранее открыть каждый документ» без основания в задании | Правило в spec и тест угадывания ID без полного верного ответа |
| Q15 | Запрос после завершения | Не изменяет reward/бюджет, безопасная ошибка; только reset открывает новый эпизод | Контракт и тест состояния |
| Q16 | Тайм-аут | Монотонные часы supervisor, принудительное завершение worker, пустой итог; reward считается по этому итогу | Детерминированные unit-тесты с контролируемыми часами + реальный timeout-тест |
| Q17 | Изоляция | Отдельный ограниченный worker и IPC без доступа к private; developer subprocess не считается полной защитой | Утверждённый способ IPC, фактический тест чтения/записи/сети |

До закрытия Q02–Q07 не расширять соответствующую финансовую часть. Можно писать независимые инфраструктурные проверки. Если внешнего ответа нет, документированное проектное решение реализуем как версионированное и заменяемое, не приписывая его организаторам.

## Что получить извне

- Официальные фиксированные проверки и интерфейсы четырёх адаптеров.
- Разрешены ли расширения схем для распределений и ID доказательств.
- Уточнения спорных границ шагов/тайм-аутов/закрытого reward при наличии официального контракта.
- Трактовка 1 ГБ и окончательные ресурсные ограничения.
- Канал сдачи, требования к демо, условия окна исправлений.

Не отправлять сообщения организаторам автоматически: подготовить конкретные вопросы для пользователя.

## Обязательный паспорт ошибки

В Б00 заполнить `docs/error_spec.json`. Для каждого типа нужны: версия, определение, исходный корректный сценарий, предусловия мутации, точное изменение, правило expected_amount_minor, валюта, округление/допуск, канонические affected_ids, допустимые наборы evidence, способ получения evidence через инструменты, чистый аналог, совместимость с другими мутациями и независимый ручной расчёт.

Для взаимодействий дополнительно: порядок мутаций, какие нарушения считаются отдельными issues, отсутствие двойного начисления за одну первопричину, что делать при компенсации/маскировке расхождений. Не выбирать случайные комбинации до проверки этих свойств.
