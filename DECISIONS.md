# Решения и открытые контракты

Редакция 3. Этот файл фиксирует рабочие решения, а не новые требования организаторов. Обозначения: принято — выбираем как проектную основу; проект — нужно утвердить примерами и проверками в указанном блоке; внешнее — требует сведений организаторов, но независимая работа продолжается.

## Обязательный паспорт ошибки

В Б00 заполнить `docs/error_spec.json`. Для каждого типа нужны: версия, определение, исходный корректный сценарий, предусловия мутации, точное изменение, правило expected_amount_minor, валюта, округление/допуск, канонические affected_ids, допустимые наборы evidence, способ получения evidence через инструменты, чистый аналог, совместимость с другими мутациями и независимый ручной расчёт.

Для взаимодействий дополнительно: порядок мутаций, какие нарушения считаются отдельными issues, отсутствие двойного начисления за одну первопричину, что делать при компенсации/маскировке расхождений. Не выбирать случайные комбинации до проверки этих свойств.

## Б00.3 — контракт действий и завершения (рабочее решение)

Ниже зафиксированы решения Q08–Q17 для реализации М01, М07–М10. Это проектные правила команды по неоднозначным границам PDF, а не опубликованный интерфейс организаторов. При получении официальных проверок сверить различия до изменения поведения.

**Envelope.** Доверенный supervisor вызывает `reset(seed, config)`, получает `(observation, info)` и передаёт worker только очищенные JSON-совместимые результаты. `observation` содержит задачу, публичный manifest, краткую policy и `remaining_steps=100`; `info` пустой или содержит лишь публичную версию API. Seed/config/error_plan/truth/provenance, закрытые пути и диагностические значения не передаются. Worker отправляет один JSON action по IPC; supervisor возвращает результат `step(action) = (observation, reward, terminated, truncated, info)`. Допустимы только `list_records(table,cursor,limit)`, `get_record(table,id)`, `get_document(doc_id)`, `calculator(expression)`, `submit({episode_id,findings})`; `submit` — одно действие. Публичный store read-only, курсор — непрозрачный снимок конкретного эпизода/таблицы, `limit` от 1 до 50. Иные ключи/типы action дают ограниченную ошибку, расходуя шаг; не раскрывать пути и traceback.

**Q08–Q09.** Шаг нумеруется от 1 до 100 и расходуется до выполнения действия. `inspection_steps` — число всех действий до submit, включая невалидные и ошибки инструментов, но не submit. Действие submit на шаге 100, успевшее до deadline, завершает `terminated=true, truncated=false` и оценивается с 99 inspection_steps. Сотое действие исследования без submit даёт `truncated=true, terminated=false`, пустой итоговый ответ и 100 inspection_steps. При исчерпанном времени submit не исполняется. Не считать вызовы reset шагами.

**Q10–Q11.** Успешные действия исследования возвращают публичный `reward=0`; в закрытом режиме terminal `reward=0` — явно обозначенный placeholder интерфейса, actual scored reward живёт у оценщика и в отдельном отчёте владельца. В открытом train terminal reward равен общей формуле PDF. Невалидная структура submit заканчивает эпизод (`terminated=true`) с фактической оценкой -1; в train возвращается -1, в closed остаётся placeholder 0. Публичный статус только `invalid_submit`, без точной подсказки о поле. Валидный, но неверный finding оценивается через FP/FN и общую формулу.

**Q12–Q14.** До нормализации строго проверить объект submit и ключи `episode_id, findings`, каждое finding с `type, affected_ids, claimed_amount_minor, currency, evidence_ids, explanation`; отклонять лишние и недостающие поля, неверные JSON-типы, bool вместо integer, нецелые/отрицательные суммы, неверный episode_id, неизвестный type, неизвестную валюту, 31+ findings, 11+ сырых evidence ID, объяснение длиннее 1000 Unicode code points. ID-списки — строки, `affected_ids` непустой, `evidence_ids` непустой; сырые повторы допускаются до лимита и затем схлопываются. Повторы между findings сохраняются. После структурной проверки неверная сумма/валюта для конкретного issue, лишний уникальный affected ID, неполный evidence set или неизвестный публичный ID внутри finding означают valid-but-wrong finding/FP. Дополнительные известные evidence ID не мешают match, если есть полный допустимый набор. Нельзя требовать предварительного открытия документа. Неразрешимое evidence ID не засчитывается, но не раскрывает наличие закрытого ID. Каноническое сравнение без порядка; one-to-one maximum matching. `explanation` — строка, содержимое на TP не влияет. Неизвестный type структурно невалиден, поскольку список типов публичен. Эти правила должны быть опубликованы с matcher и испытаны атакующими примерами.

**Q15–Q16.** После terminated/truncated любой step даёт безопасную ошибку `episode_closed`, не меняет счётчики и награду; только доверенный reset открывает новый эпизод. Supervisor держит monotonic deadline (целевой лимит 60 секунд на эпизод), принудительно останавливает зависший worker, формирует пустой итог при тайм-ауте и ставит truncated. Награду считает по общей формуле по пустому ответу и фактически потраченным inspection_steps; не назначать автоматически -1, кроме структурно невалидного submit. Deadline измеряется внешним временем, поэтому точный replay гарантирует данные/переходы/награды при контролируемых часах или одинаковом отсутствии timeout; реальное истечение проверяется отдельно. Падение worker трактуется как truncated с пустым ответом, причина остаётся в закрытой диагностике.

**Q17.** IPC — локальный канал типизированных JSON сообщений request/response между ограниченным worker и доверенным supervisor; только пять разрешённых действий, без методов чтения файлов или оценщика. Максимальные размеры сообщений и timeout нужно задать при Б04. В проверочном режиме worker запускается в отдельном контейнере с read-only runtime, без сети и private mounts; supervisor/evaluator остаются снаружи. Developer subprocess маркируется как не изолированный. До объявления изоляции проверить чтение private, запись в оценщик, сеть и утечки через каждый публичный выход. Если ограниченный контейнер не удастся обеспечить локально, тест выполняется в CI, но без фактической проверки прав Б04 не закрывается.

| Случай | Результат step | Scored reward / доступ worker |
|---|---|---|
| reset | публичные task/manifest/policy/100 шагов | нет оценки, seed скрыт |
| Исследование на шаге 1–99, включая ограниченную ошибку | 0, false, false; шаг потрачен | 0 в обоих режимах |
| Правильный submit на шаге 100 до deadline | terminated=true, truncated=false | formula с 99 inspection_steps; в closed worker видит 0 |
| Сотое исследование | terminated=false, truncated=true; пустой итог | formula по пустому ответу с 100 inspection_steps; closed 0 |
| Невалидный submit | terminated=true, truncated=false | -1; в closed worker видит 0 |
| Timeout до submit, включая попытку submit после deadline | truncated=true; пустой итог | formula по пустому ответу; closed 0 |
| step после закрытия | `episode_closed`, без изменения состояния | прежняя оценка не выдаётся заново |

Открытые внешние вопросы: точная схема адаптеров и опубликованные фиксированные проверки, трактовка закрытого terminal reward и границы 100-го шага, канал сдачи. Они не блокируют реализацию документированного рабочего контракта. Если официальный контракт противоречит ему, изменить DECISIONS/PLAN и тесты с указанием причины; не приписывать эти решения PDF.
