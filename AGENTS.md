# Обязательные инструкции проекта GENESIS FinTech

## Утверждённая основа

Пользователь утвердил редакцию 4 плана и поручил следовать ей до завершения проекта. Не начинать планирование заново и не заменять согласованную архитектуру без конкретного основания.

Перед работой прочитать текущий `PLAN.md`, затем относящиеся к задаче разделы `DECISIONS.md`, `REQUIREMENTS.md` и `docs/MODULES.md`. Проверить фактическое состояние файлов и выполненных проверок: план не является доказательством реализации.

Источники истины:
- `genesis.pdf` — исходные условия организаторов.
- `PLAN.md` — порядок задач, текущий прогресс и критерии готовности.
- `REQUIREMENTS.md` — покрытие требований и ссылки на фактические проверки по мере реализации.
- `docs/MODULES.md` — архитектура и ответственность модулей.
- `DECISIONS.md` — принятые решения и открытые контракты.
- `docs/error_spec.json` — спецификация ошибок после её создания; пока она запланирована.
- `GENESIS_FULL_PLAN.md` — полный объединённый документ для пользователя, синхронизируемый с четырьмя исходными Markdown-документами выше (PLAN, MODULES, REQUIREMENTS, DECISIONS).

Текущие явные инструкции пользователя имеют приоритет. При противоречии плана заданию показать конкретное расхождение, исправить план с указанием причины и следовать подтверждённым условиям; не приписывать предположения организаторам.

## Порядок работы

Основной маршрут: Б00 → Б01 → Б02 → Б03A → Б03B → Б04 → Б05 → Б06 → Б07 → Б08 → Б09. Независимая работа Б04/Б05 допустима только на условиях PLAN.md. Разбиение на модули не является разрешением запускать дополнительных агентов.

Работать по ID задачи и её критерию готовности. При запросе продолжить проект брать следующую незавершённую задачу из PLAN.md. Не запрашивать повторного согласования уже утверждённой стратегии; рутинные решения принимать самостоятельно в пределах задачи. Если задача пользователя ограничена документами, не начинать реализацию автоматически.

Не расширять область проекта: UI, LLM/API, обучение весов, GPU, БД и облачные сервисы не входят в обязательную реализацию. Использовать Python 3.11 и согласованный минимальный стек. Для сроков сокращать только необязательный объём, не требования задания.

## Обязательные инженерные правила

- Сначала согласованная финансовая история, затем контролируемые причинные изменения.
- Не путать дублирование счёта с произвольным повтором платежа; частичная оплата сама по себе не ошибка.
- Деньги — целые минимальные единицы, FX — Decimal и явно объявленное округление; не использовать float для денежных расчётов.
- Разделять генерацию truth, независимую проверку по публичным данным и matcher. Oracle не доказывает корректность эталона.
- Каждый тип ошибки имеет формальную семантику, ручной пример, чистый аналог и доступные доказательства.
- Агент работает только через публичный интерфейс. Seed, truth, provenance и диагностика оценщика не передаются worker.
- Отдельный процесс не заменяет проверку фактических прав доступа; developer-режим не выдавать за полноценную изоляцию.
- Сохранять общий контракт reset/step и общую награду задания. Различать фактическую оценку и доступный агенту reward в закрытом режиме.
- Тестировать утечки, атаки, воспроизводимость и преобразования по мере разработки, не откладывать до Б07.
- Не ослаблять тесты ради прохождения; при ошибке теста сначала сверить его с заданием и контрактом.
- Официальный проверочный запуск — без сети, платных API и GPU; подготовку зависимостей отличать от offline-запуска.

## Прогресс и изменения

После завершённой задачи обновить её статус в PLAN.md, перечислить фактически выполненные проверки и следующий шаг. Частичную работу отмечать как частичную. Не считать Б00.4 завершённым только из-за наличия этого файла: нужны также закреплённые контракты и приёмка Б00.

Изменения семантики/архитектуры отражать в DECISIONS.md с причиной и затронутыми задачами/проверками. Обычные исправления и выполнение задач не требуют повторного утверждения плана. Существенное изменение пользовательского объёма согласовать, если оно ещё не авторизовано; независимую работу продолжать.

При изменении любого из четырёх документов плана пересобрать GENESIS_FULL_PLAN.md без пропусков, сохранив оглавление. Вносить изменения в исходные документы, а не только в объединённую копию.

После блока сообщать по-русски кратко: что реализовано, чем проверено, что осталось, следующий шаг. Не обещать отсутствие ошибок или баллы жюри без доказательств. Завершение проекта — только после К9 и полного комплекта сдачи; внешняя публикация/отправка выполняется по указанию пользователя.
