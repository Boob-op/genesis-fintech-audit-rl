## Как пользоваться планом

| Документ | Что является источником истины |
|---|---|
| `genesis.pdf` | Условия организаторов |
| `PLAN.md` | Очерёдность, задачи, статусы, критерии готовности |
| `REQUIREMENTS.md` | Покрытие требований задания реализацией и проверками |
| `docs/MODULES.md` | Ответственность, файлы, зависимости и границы модулей |
| `DECISIONS.md` | Принятые решения, временные предположения и открытые вопросы |
| `docs/error_spec.json` — версия 1.0.0 | Формальная семантика четырёх типов ошибок |

Блок — законченный результат разработки. Модуль — участок кода с одной ответственностью. Один модуль может развиваться в нескольких блоках: это не дублирование реализации. Если меняется контракт, обновить его источник истины и затронутые проверки; не создавать расходящиеся копии правила в документах.

Обозначения М01–М14 раскрыты в `docs/MODULES.md`, R01–R46 — в `REQUIREMENTS.md`, Q01–Q17 — в `DECISIONS.md`. Все пути исходников и тестов пока планируемые.

## Цель и границы

Создать воспроизводимую среду финансового аудита: генератор синтетических компаний, контролируемые ошибки, ограниченные инструменты агента, независимый оценщик и проверочный запуск без сети, платных API и GPU.

Основа: Python 3.11, стандартная библиотека, Pydantic v2, pytest, фиксированные зависимости и контейнер. UI, база данных, облачная инфраструктура, LLM и обучение весов в обязательную реализацию не входят.

Каждый блок заканчивается работающим результатом и проверками. Не объявляем блок готовым по одному наличию файлов. Не заменяем проверку корректности высоким результатом oracle.

## Порядок

Б00 → Б01 → Б02 → Б03A → Б03B → Б04/Б05 → Б06 → Б07 → Б08 → Б09.

После Б03B работу над данными Б05 можно вести независимо от завершения Б04, если семантика соответствующей ошибки закреплена в Б00. Интеграционная приёмка Б05 требует готового Б04. Это возможность распределения работы в команде, а не требование запускать несколько агентов.

При работе одним исполнителем порядок по умолчанию: полностью Б04, затем Б05. Одновременно открывать не больше одного основного блока; независимые исправления текущих проверок допустимы. Б07 — итоговая кампания проверки, тесты пишутся раньше.

Документация, тесты и контейнер обновляются по ходу работы. Первый сквозной результат — Б03B. Полное покрытие типов ошибок — Б05. Готовность к сдаче — Б09.

## Минимальная сдача и независимая проверка

Не сокращаем: четыре типа ошибок, два сценария взаимодействия, чистые и отвлекающие случаи, пять действий, лимит 100 шагов, отдельный оценщик, общий matcher и награду, четыре адаптера, тесты, 10 train + 10 dev, траектории, исходники с лицензией, инструкции контейнера, единую команду проверки, описание устройства и демо.

Сокращаем при необходимости: дополнительные сценарии сверх двух, объём данных в пределах допустимых требований, дополнительные наборы и разнообразие сверх обязательного. UI, LLM и обучение весов не добавляем до готовности обязательной сдачи. Простая команда запуска не заменяет требуемые инструкции контейнера.

Для каждого блока, меняющего данные или оценку, критерий приёмки: независимый проверяющий может восстановить правильный ответ по публичным записям и политике без truth/provenance. Он использует ту же спецификацию, но независимый расчёт и вручную проверенные мини-примеры. Перекрёстное ревью желательно; количество разработчиков само по себе не доказывает независимость проверки.

Принятые уточнения к доработкам: обязательный первый тип остаётся дублем счёта, а не произвольной проводки; нулевой допуск не отменяет объявленное округление; общая спецификация не должна создавать общий источник вычислительной ошибки; ограничения журналов относятся к видимым агенту данным, закрытая диагностика оценщика хранится отдельно.

## Риски, которые проверяем заранее

| Риск | Ранний сигнал | Действие |
|---|---|---|
| Невозможно доказать нарушение | Нужен скрытый факт или отсутствующий документ | Исправить публичные данные/политику в Б00–Б03A |
| Эталон и проверяющий ошибаются одинаково | Обе стороны вызывают одну функцию расчёта нарушения | Независимый расчёт + ручной пример |
| Дубль определяется по порядку ID | После rename меняется «лишний» счёт | Канонический набор участников нарушения без зависимости от случайного ID |
| Мутации маскируют друг друга | Одна ошибка исчезает или сумма становится неоднозначной | Проверить порядок и предусловия, не генерировать неподдерживаемую комбинацию |
| Изоляция только на словах | Worker может открыть private-файл по пути | Реальная граница доступа, тест чтения/записи, разделение developer/isolated |
| Слишком большой эпизод | Даже известный путь расследования не укладывается в бюджет | Уменьшить размер/связность, не добавлять запрещённые инструменты |
| Зависимость от платформенного времени | Replay различается по времени выполнения | Детерминированные переходы проверять с контролируемыми часами; реальный тайм-аут отдельно |
| Награда при truncation трактуется произвольно | Везде автоматически присваивается -1 | Следовать пустому итогу и общей формуле, отдельно от invalid submit; уточнить официальный контракт |
| Нехватка времени | Не закрыта текущая контрольная точка | Сократить необязательное разнообразие, не обязательную корректность |

## Запланированные команды и критерии их успеха

`verify` уже реализован для основы разработки; `verify --full` возвращает код 2. Остальные команды ниже пока запланированы:

```text
python -m fintech_audit_rl verify
python -m fintech_audit_rl demo
python -m fintech_audit_rl generate --config <path> --seed <integer> --output <path>
python -m fintech_audit_rl benchmark --suite <path> --output <path>
```

`verify` — одна официальная точка проверки: запускает обязательные тесты и контрольный прогон, возвращает ненулевой exit code при провале, сохраняет отчёт. До готовности всего набора явно пишет доступное покрытие; не сообщает «полная проверка пройдена» для частичного прототипа. Аргументы seed/config доступны доверенному CLI, не worker.

`demo` — короткий фиксированный сценарий с понятными результатами. `generate` — создание данных без перезаписи существующих результатов по умолчанию. `benchmark` — четыре адаптера и отчёт. Сборка/установка могут требовать сеть заранее, проверочный запуск подготовленного окружения — без сети.

## Короткий итоговый чек-лист

Этот список не заменяет R01–R46 и ресурсные проверки; это десять наблюдаемых результатов для итогового прогона и демо. Пока ни один не отмечен выполненным.

- [ ] Чистая компания + пустой submit: P=0, R=0, F1=1.
- [ ] Ошибочная компания + oracle: F1=1, reward=clip(1-0.002*inspection_steps,-1,1); значение 1 только при нуле шагов исследования.
- [ ] Ошибочная компания + пустой submit: F1=0.
- [ ] Flag-all на заранее определённом наборе атак даёт плохой результат; не требовать этого от любого случайно угаданного полного правильного ответа.
- [ ] Повторные findings не добавляют TP и учитываются как FP.
- [ ] Одинаковые seed/config/версии/действия воспроизводят записи, переходы и награды, а не только начальные данные.
- [ ] Переименование всех ID и ссылок сохраняет правильность oracle и соответствующую награду.
- [ ] Перестановка строк сохраняет правильность oracle и соответствующую награду.
- [ ] Observation/info/ошибки не раскрывают закрытые данные; права worker проверены отдельно.
- [ ] Одна команда запускает полную проверку в подготовленном автономном окружении и сообщает провал ненулевым exit code.

Для инфраструктурных блоков критерий — корректность контракта и запуска. Для блоков данных и оценки дополнительно обязателен независимый вывод по публичным данным: не применять финансовый критерий буквально к настройке окружения.

## Формат отчёта по блоку

1. Что реализовано.
2. Какие проверки фактически запущены и их результат.
3. Какие ограничения и вопросы остались.
4. Какой блок следующий.

Выполненные задачи отмечаются только по факту. Существенные изменения плана фиксируются вместе с причиной.
