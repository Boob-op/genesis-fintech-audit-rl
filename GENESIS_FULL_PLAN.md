## Как пользоваться планом

| Документ | Что является источником истины |
|---|---|
| `genesis.pdf` | Условия организаторов |
| `PLAN.md` | Очерёдность, задачи, статусы, критерии готовности |
| `REQUIREMENTS.md` | Покрытие требований задания реализацией и проверками |
| `docs/MODULES.md` | Ответственность, файлы, зависимости и границы модулей |
| `DECISIONS.md` | Принятые решения, временные предположения и открытые вопросы |
| `docs/error_spec.json` — версия 1.0.0 | Формальная семантика четырёх типов ошибок |

Блок — законченный результат разработки. Модуль — участок кода с одной ответственностью. Один модуль может развиваться в нескольких блоках: это не дублирование реализации. Если меняется контракт, обновить его источник истины и затронутые проверки; не создавать расходящиеся копии правила в документах.

Обозначения М01–М14 раскрыты в `docs/MODULES.md`, R01–R46 — в `REQUIREMENTS.md`, Q01–Q17 — в `DECISIONS.md`. Все пути исходников и тестов пока планируемые.

## Цель и границы

Создать воспроизводимую среду финансового аудита: генератор синтетических компаний, контролируемые ошибки, ограниченные инструменты агента, независимый оценщик и проверочный запуск без сети, платных API и GPU.

Основа: Python 3.11, стандартная библиотека, Pydantic v2, pytest, фиксированные зависимости и контейнер. UI, база данных, облачная инфраструктура, LLM и обучение весов в обязательную реализацию не входят.

Каждый блок заканчивается работающим результатом и проверками. Не объявляем блок готовым по одному наличию файлов. Не заменяем проверку корректности высоким результатом oracle.

## Порядок

Б00 → Б01 → Б02 → Б03A → Б03B → Б04/Б05 → Б06 → Б07 → Б08 → Б09.

После Б03B работу над данными Б05 можно вести независимо от завершения Б04, если семантика соответствующей ошибки закреплена в Б00. Интеграционная приёмка Б05 требует готового Б04. Это возможность распределения работы в команде, а не требование запускать несколько агентов.

При работе одним исполнителем порядок по умолчанию: полностью Б04, затем Б05. Одновременно открывать не больше одного основного блока; независимые исправления текущих проверок допустимы. Б07 — итоговая кампания проверки, тесты пишутся раньше.

Документация, тесты и контейнер обновляются по ходу работы. Первый сквозной результат — Б03B. Полное покрытие типов ошибок — Б05. Готовность к сдаче — Б09.

## Минимальная сдача и независимая проверка

Не сокращаем: четыре типа ошибок, два сценария взаимодействия, чистые и отвлекающие случаи, пять действий, лимит 100 шагов, отдельный оценщик, общий matcher и награду, четыре адаптера, тесты, 10 train + 10 dev, траектории, исходники с лицензией, инструкции контейнера, единую команду проверки, описание устройства и демо.

Сокращаем при необходимости: дополнительные сценарии сверх двух, объём данных в пределах допустимых требований, дополнительные наборы и разнообразие сверх обязательного. UI, LLM и обучение весов не добавляем до готовности обязательной сдачи. Простая команда запуска не заменяет требуемые инструкции контейнера.

Для каждого блока, меняющего данные или оценку, критерий приёмки: независимый проверяющий может восстановить правильный ответ по публичным записям и политике без truth/provenance. Он использует ту же спецификацию, но независимый расчёт и вручную проверенные мини-примеры. Перекрёстное ревью желательно; количество разработчиков само по себе не доказывает независимость проверки.

Принятые уточнения к доработкам: обязательный первый тип остаётся дублем счёта, а не произвольной проводки; нулевой допуск не отменяет объявленное округление; общая спецификация не должна создавать общий источник вычислительной ошибки; ограничения журналов относятся к видимым агенту данным, закрытая диагностика оценщика хранится отдельно.

| Эталон и проверяющий ошибаются одинаково | Обе стороны вызывают одну функцию расчёта нарушения | Независимый расчёт + ручной пример |
| Дубль определяется по порядку ID | После rename меняется «лишний» счёт | Канонический набор участников нарушения без зависимости от случайного ID |
| Мутации маскируют друг друга | Одна ошибка исчезает или сумма становится неоднозначной | Проверить порядок и предусловия, не генерировать неподдерживаемую комбинацию |
| Изоляция только на словах | Worker может открыть private-файл по пути | Реальная граница доступа, тест чтения/записи, разделение developer/isolated |
| Слишком большой эпизод | Даже известный путь расследования не укладывается в бюджет | Уменьшить размер/связность, не добавлять запрещённые инструменты |
| Зависимость от платформенного времени | Replay различается по времени выполнения | Детерминированные переходы проверять с контролируемыми часами; реальный тайм-аут отдельно |
| Награда при truncation трактуется произвольно | Везде автоматически присваивается -1 | Следовать пустому итогу и общей формуле, отдельно от invalid submit; уточнить официальный контракт |
| Нехватка времени | Не закрыта текущая контрольная точка | Сократить необязательное разнообразие, не обязательную корректность |

## 2. Поток данных

```text
Доверенный supervisor
  seed + config
       → M03: правильная история
       → M06: проверка исходных данных
       → M04: внесение ошибок
       → M05: public + private bundles
       → M06: независимая проверка публичных данных и сравнение с truth

public bundle → M07 → M08: инструменты ← IPC → worker с M11
private bundle → M09: оценщик ← submit от M08 через supervisor
                                              ↓
                          M12: траектория и закрытая диагностика
                                              ↓
                          M13/M14: итоговый отчёт и команда проверки
```

Supervisor вызывает `reset(seed, config)` на доверенной стороне. Worker получает результат reset, но не аргументы. Следовательно, контракт reset сохраняется, а агент не узнаёт seed. Обычная политика не держит прямую ссылку на объект среды или Episode.

## 3. Правила зависимостей

- М01 — базовый слой: не импортирует генератор, среду и оценщик. М02 зависит от публичных схем и публичной спецификации.
- М03 и М04 используют М01/М02. М05 собирает их результат. Генерация не зависит от политик или matcher.
- М06 не импортирует `generator/truth.py` и `errors/*`. Допустимы схемы и парсинг; критические ожидаемые суммы проверяются независимым расчётом и ручными эталонными примерами, не одной и той же функцией с генератором.
- М07 принимает только публичную часть; не принимает целый объект с truth, seed или provenance.
- М08 использует М01/М07 и узкий канал отправки ответа оценщику. Оно не импортируется worker как привилегированный объект.
- М09 использует схемы и публичную спецификацию, но не генератор. Matcher сопоставляет поля; он не заменяет М06.
- М10 собирает компоненты, управляет жизненным циклом. Инфраструктурные зависимости направлены внутрь, бизнес-модули не импортируют CLI.
- Обычные М11 используют только публичные модели и клиент протокола. `evaluation/oracle.py` никогда не входит в обычный policy worker.
- М12 получает события явно; не сериализует весь объект Episode или traceback.
- М13 вызывает компоненты через явные интерфейсы. Преобразования последовательно обновляют все ID, ссылки, evidence и эталон на доверенной стороне.

Проверка импортов полезна, но сама по себе не является защитой от чтения файлов произвольным Python-кодом.

## 4. Граница доверия и режимы запуска

| Зона | Что доступно | Что запрещено |
|---|---|---|
| Supervisor / генератор | Seed/config, история, обе части эпизода | Передача закрытой части в worker |
| Оценщик | Truth, provenance для диагностики, публичные документы, submit | Запись со стороны агента, диагностика в закрытом observation/info |
| Сервер инструментов | Публичные записи read-only, состояние бюджета | Чтение произвольных путей по action |
| Обычный worker | Наблюдения, код политики, локальное состояние вычислений | Файлы эпизода/оценщика, сеть, shell/SQL как инструменты, чужая память и закрытые журналы |
| Oracle | Доверенный адаптер оценщика с truth | Запуск с эталоном под видом обычной политики |

Отдельный процесс не запрещает чтение файлов того же пользователя. В Б04 проверяем реальную модель запуска: отдельный ограниченный worker/container с read-only runtime, без mounts private-данных, без сети и с ограниченным IPC; оценщик остаётся вне доступной ему области. Способ IPC и совместимость с адаптерами организаторов фиксируются до реализации Б04. Если локальный developer-режим использует только subprocess, явно маркируем его как не подтверждающий полноценную изоляцию.

Встроенные инструменты не дают свободный shell/SQL/доступ к FS. Runtime Python всё равно читает свои библиотеки — это не означает доступ агента к произвольным файлам хоста. Различаем API-ограничения и OS-изоляцию; проверяем оба.

## 5. Размещение файлов данных

Планируемая структура одного экспортированного эпизода:

```text
episodes/train/<opaque_episode_id>/
  public/
    manifest.json
    ledger.csv
    invoices.jsonl
    payments.jsonl
    fx.csv
    policy.json
  private/
    truth.json
    provenance.json
    generation.json          # seed/config/версии для воспроизведения
```

Та же структура у dev; публичный интерфейс показывает только содержимое разрешённых записей, не пути. Каталоги `public/private` — соглашение хранения, а не security boundary. В проверочном запуске private не монтируется в worker. Открытые seed/config train/dev доступны разработчику в комплекте, но не передаются политике в наблюдениях. Внутренние holdout-наборы хранятся отдельно от train/dev.

```text
runs/<run_id>/
  trajectories.jsonl         # журнал владельца запуска; наблюдения очищены
  report.json                # итоговые метрики после прогона
  private/diagnostics.jsonl  # закрытая диагностика оценщика
```

Worker не читает ни один файл runs. В closed-режиме реальный reward можно записать доверенным логгером, но нельзя передать агенту до конца проверки. Agent-visible reward и scored reward различаются явно; итоговые траектории не должны выдавать placeholder за фактическую награду.

## 6. Поведение оценщика

1. Проверить структуру полного submit, episode_id и лимиты до нормализации.
2. Нормализовать разрешённым и опубликованным способом; не удалять лишние уникальные ID.
3. Построить допустимые пары finding ↔ truth issue по типу, affected_ids, сумме, валюте и полному evidence set.
4. Получить детерминированное взаимно однозначное сопоставление максимальной мощности. Tie-break не должен менять число TP при перестановке findings.
5. Несопоставленные findings, включая повторы, → FP; несопоставленные issues → FN.
6. Вычислить P/R/F1 и общую награду; explanation не влияет на TP, кроме структурного лимита.
7. Реальную оценку передать только разрешённому получателю для режима запуска.

Важно: oracle может быть полностью правильным, но это не доказывает правильность truth. М06 выполняется отдельно. Не требовать от простой политики идеальной полноты на всех сложных случаях как условия корректности среды.

## Как отмечать готовность

При реализации добавлять к строке ссылку на фактический тест/артефакт и результат проверочного запуска. Наличие плана теста не означает выполнения требования. Точные 20+20+20 проверки жюри неизвестны; наши проверки не называем официальными и не обещаем баллы по их числу.

## Б00.3 — контракт действий и завершения (рабочее решение)

Ниже зафиксированы решения Q08–Q17 для реализации М01, М07–М10. Это проектные правила команды по неоднозначным границам PDF, а не опубликованный интерфейс организаторов. При получении официальных проверок сверить различия до изменения поведения.

**Envelope.** Доверенный supervisor вызывает `reset(seed, config)`, получает `(observation, info)` и передаёт worker только очищенные JSON-совместимые результаты. `observation` содержит задачу, публичный manifest, краткую policy и `remaining_steps=100`; `info` пустой или содержит лишь публичную версию API. Seed/config/error_plan/truth/provenance, закрытые пути и диагностические значения не передаются. Worker отправляет один JSON action по IPC; supervisor возвращает результат `step(action) = (observation, reward, terminated, truncated, info)`. Допустимы только `list_records(table,cursor,limit)`, `get_record(table,id)`, `get_document(doc_id)`, `calculator(expression)`, `submit({episode_id,findings})`; `submit` — одно действие. Публичный store read-only, курсор — непрозрачный снимок конкретного эпизода/таблицы, `limit` от 1 до 50. Иные ключи/типы action дают ограниченную ошибку, расходуя шаг; не раскрывать пути и traceback.

**Q08–Q09.** Шаг нумеруется от 1 до 100 и расходуется до выполнения действия. `inspection_steps` — число всех действий до submit, включая невалидные и ошибки инструментов, но не submit. Действие submit на шаге 100, успевшее до deadline, завершает `terminated=true, truncated=false` и оценивается с 99 inspection_steps. Сотое действие исследования без submit даёт `truncated=true, terminated=false`, пустой итоговый ответ и 100 inspection_steps. При исчерпанном времени submit не исполняется. Не считать вызовы reset шагами.

**Q10–Q11.** Успешные действия исследования возвращают публичный `reward=0`; в закрытом режиме terminal `reward=0` — явно обозначенный placeholder интерфейса, actual scored reward живёт у оценщика и в отдельном отчёте владельца. В открытом train terminal reward равен общей формуле PDF. Невалидная структура submit заканчивает эпизод (`terminated=true`) с фактической оценкой -1; в train возвращается -1, в closed остаётся placeholder 0. Публичный статус только `invalid_submit`, без точной подсказки о поле. Валидный, но неверный finding оценивается через FP/FN и общую формулу.

**Q12–Q14.** До нормализации строго проверить объект submit и ключи `episode_id, findings`, каждое finding с `type, affected_ids, claimed_amount_minor, currency, evidence_ids, explanation`; отклонять лишние и недостающие поля, неверные JSON-типы, bool вместо integer, нецелые/отрицательные суммы, неверный episode_id, неизвестный type, неизвестную валюту, 31+ findings, 11+ сырых evidence ID, объяснение длиннее 1000 Unicode code points. ID-списки — строки, `affected_ids` непустой, `evidence_ids` непустой; сырые повторы допускаются до лимита и затем схлопываются. Повторы между findings сохраняются. После структурной проверки неверная сумма/валюта для конкретного issue, лишний уникальный affected ID, неполный evidence set или неизвестный публичный ID внутри finding означают valid-but-wrong finding/FP. Дополнительные известные evidence ID не мешают match, если есть полный допустимый набор. Нельзя требовать предварительного открытия документа. Неразрешимое evidence ID не засчитывается, но не раскрывает наличие закрытого ID. Каноническое сравнение без порядка; one-to-one maximum matching. `explanation` — строка, содержимое на TP не влияет. Неизвестный type структурно невалиден, поскольку список типов публичен. Эти правила должны быть опубликованы с matcher и испытаны атакующими примерами.

**Q15–Q16.** После terminated/truncated любой step даёт безопасную ошибку `episode_closed`, не меняет счётчики и награду; только доверенный reset открывает новый эпизод. Supervisor держит monotonic deadline (целевой лимит 60 секунд на эпизод), принудительно останавливает зависший worker, формирует пустой итог при тайм-ауте и ставит truncated. Награду считает по общей формуле по пустому ответу и фактически потраченным inspection_steps; не назначать автоматически -1, кроме структурно невалидного submit. Deadline измеряется внешним временем, поэтому точный replay гарантирует данные/переходы/награды при контролируемых часах или одинаковом отсутствии timeout; реальное истечение проверяется отдельно. Падение worker трактуется как truncated с пустым ответом, причина остаётся в закрытой диагностике.

**Q17.** IPC — локальный канал типизированных JSON сообщений request/response между ограниченным worker и доверенным supervisor; только пять разрешённых действий, без методов чтения файлов или оценщика. Максимальные размеры сообщений и timeout нужно задать при Б04. В проверочном режиме worker запускается в отдельном контейнере с read-only runtime, без сети и private mounts; supervisor/evaluator остаются снаружи. Developer subprocess маркируется как не изолированный. До объявления изоляции проверить чтение private, запись в оценщик, сеть и утечки через каждый публичный выход. Если ограниченный контейнер не удастся обеспечить локально, тест выполняется в CI, но без фактической проверки прав Б04 не закрывается.

| Случай | Результат step | Scored reward / доступ worker |
|---|---|---|
| reset | публичные task/manifest/policy/100 шагов | нет оценки, seed скрыт |
| Исследование на шаге 1–99, включая ограниченную ошибку | 0, false, false; шаг потрачен | 0 в обоих режимах |
| Правильный submit на шаге 100 до deadline | terminated=true, truncated=false | formula с 99 inspection_steps; в closed worker видит 0 |
| Сотое исследование | terminated=false, truncated=true; пустой итог | formula по пустому ответу с 100 inspection_steps; closed 0 |
| Невалидный submit | terminated=true, truncated=false | -1; в closed worker видит 0 |
| Timeout до submit, включая попытку submit после deadline | truncated=true; пустой итог | formula по пустому ответу; closed 0 |
| step после закрытия | `episode_closed`, без изменения состояния | прежняя оценка не выдаётся заново |

Открытые внешние вопросы: точная схема адаптеров и опубликованные фиксированные проверки, трактовка закрытого terminal reward и границы 100-го шага, канал сдачи. Они не блокируют реализацию документированного рабочего контракта. Если официальный контракт противоречит ему, изменить DECISIONS/PLAN и тесты с указанием причины; не приписывать эти решения PDF.
