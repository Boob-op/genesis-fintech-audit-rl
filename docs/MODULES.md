## 2. Поток данных

```text
Доверенный supervisor
  seed + config
       → M03: правильная история
       → M06: проверка исходных данных
       → M04: внесение ошибок
       → M05: public + private bundles
       → M06: независимая проверка публичных данных и сравнение с truth

public bundle → M07 → M08: инструменты ← IPC → worker с M11
private bundle → M09: оценщик ← submit от M08 через supervisor
                                              ↓
                          M12: траектория и закрытая диагностика
                                              ↓
                          M13/M14: итоговый отчёт и команда проверки
```

Supervisor вызывает `reset(seed, config)` на доверенной стороне. Worker получает результат reset, но не аргументы. Следовательно, контракт reset сохраняется, а агент не узнаёт seed. Обычная политика не держит прямую ссылку на объект среды или Episode.

## 3. Правила зависимостей

- М01 — базовый слой: не импортирует генератор, среду и оценщик. М02 зависит от публичных схем и публичной спецификации.
- М03 и М04 используют М01/М02. М05 собирает их результат. Генерация не зависит от политик или matcher.
- М06 не импортирует `generator/truth.py` и `errors/*`. Допустимы схемы и парсинг; критические ожидаемые суммы проверяются независимым расчётом и ручными эталонными примерами, не одной и той же функцией с генератором.
- М07 принимает только публичную часть; не принимает целый объект с truth, seed или provenance.
- М08 использует М01/М07 и узкий канал отправки ответа оценщику. Оно не импортируется worker как привилегированный объект.
- М09 использует схемы и публичную спецификацию, но не генератор. Matcher сопоставляет поля; он не заменяет М06.
- М10 собирает компоненты, управляет жизненным циклом. Инфраструктурные зависимости направлены внутрь, бизнес-модули не импортируют CLI.
- Обычные М11 используют только публичные модели и клиент протокола. `evaluation/oracle.py` никогда не входит в обычный policy worker.
- М12 получает события явно; не сериализует весь объект Episode или traceback.
- М13 вызывает компоненты через явные интерфейсы. Преобразования последовательно обновляют все ID, ссылки, evidence и эталон на доверенной стороне.

Проверка импортов полезна, но сама по себе не является защитой от чтения файлов произвольным Python-кодом.

## 4. Граница доверия и режимы запуска

| Зона | Что доступно | Что запрещено |
|---|---|---|
| Supervisor / генератор | Seed/config, история, обе части эпизода | Передача закрытой части в worker |
| Оценщик | Truth, provenance для диагностики, публичные документы, submit | Запись со стороны агента, диагностика в закрытом observation/info |
| Сервер инструментов | Публичные записи read-only, состояние бюджета | Чтение произвольных путей по action |
| Обычный worker | Наблюдения, код политики, локальное состояние вычислений | Файлы эпизода/оценщика, сеть, shell/SQL как инструменты, чужая память и закрытые журналы |
| Oracle | Доверенный адаптер оценщика с truth | Запуск с эталоном под видом обычной политики |

Отдельный процесс не запрещает чтение файлов того же пользователя. В Б04 проверяем реальную модель запуска: отдельный ограниченный worker/container с read-only runtime, без mounts private-данных, без сети и с ограниченным IPC; оценщик остаётся вне доступной ему области. Способ IPC и совместимость с адаптерами организаторов фиксируются до реализации Б04. Если локальный developer-режим использует только subprocess, явно маркируем его как не подтверждающий полноценную изоляцию.

Встроенные инструменты не дают свободный shell/SQL/доступ к FS. Runtime Python всё равно читает свои библиотеки — это не означает доступ агента к произвольным файлам хоста. Различаем API-ограничения и OS-изоляцию; проверяем оба.

## 5. Размещение файлов данных

Планируемая структура одного экспортированного эпизода:

```text
episodes/train/<opaque_episode_id>/
  public/
    manifest.json
    ledger.csv
    invoices.jsonl
    payments.jsonl
    fx.csv
    policy.json
  private/
    truth.json
    provenance.json
    generation.json          # seed/config/версии для воспроизведения
```

Та же структура у dev; публичный интерфейс показывает только содержимое разрешённых записей, не пути. Каталоги `public/private` — соглашение хранения, а не security boundary. В проверочном запуске private не монтируется в worker. Открытые seed/config train/dev доступны разработчику в комплекте, но не передаются политике в наблюдениях. Внутренние holdout-наборы хранятся отдельно от train/dev.

```text
runs/<run_id>/
  trajectories.jsonl         # журнал владельца запуска; наблюдения очищены
  report.json                # итоговые метрики после прогона
  private/diagnostics.jsonl  # закрытая диагностика оценщика
```

Worker не читает ни один файл runs. В closed-режиме реальный reward можно записать доверенным логгером, но нельзя передать агенту до конца проверки. Agent-visible reward и scored reward различаются явно; итоговые траектории не должны выдавать placeholder за фактическую награду.

## 6. Поведение оценщика

1. Проверить структуру полного submit, episode_id и лимиты до нормализации.
2. Нормализовать разрешённым и опубликованным способом; не удалять лишние уникальные ID.
3. Построить допустимые пары finding ↔ truth issue по типу, affected_ids, сумме, валюте и полному evidence set.
4. Получить детерминированное взаимно однозначное сопоставление максимальной мощности. Tie-break не должен менять число TP при перестановке findings.
5. Несопоставленные findings, включая повторы, → FP; несопоставленные issues → FN.
6. Вычислить P/R/F1 и общую награду; explanation не влияет на TP, кроме структурного лимита.
7. Реальную оценку передать только разрешённому получателю для режима запуска.

Важно: oracle может быть полностью правильным, но это не доказывает правильность truth. М06 выполняется отдельно. Не требовать от простой политики идеальной полноты на всех сложных случаях как условия корректности среды.
